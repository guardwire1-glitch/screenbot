# ScreenBot Class Mode: Known Failure Modes & Mitigations (RISKS.md)

Scope: the Windows live-class path only — stable capture → Gemini extraction → line consensus → append-only merge → editor delivery → undo. This document separates what the offline test suite actually proves from what still needs a real screen, editor, and API session.

**Verification legend**

- **Automated** — covered by `pytest tests`; the relevant logic runs in the test process.
- **Automated (mocked boundary)** — logic is tested, but Win32 capture/keystroke, a real editor, or the live Gemini API is replaced by a test double.
- **Partial** — core guard is tested; important integration behavior is manual-only.
- **Residual** — known limitation, not fully mitigated. Do not treat it as solved.

The suite does not call the live Gemini API, does not drive a real VS Code or Visual Studio window (DTE is a simulated COM object), and does not exercise a real lecture capture. Those remain manual release checks. The VS Code-family extension has a Node test suite with a mocked `vscode` module; it is not installed into a real editor by CI.

## Residual risks and limitations

These are not claimed as solved.

1. **Untrusted saved-state signals in non-bridge IDEs.** JetBrains, Eclipse, NetBeans, SSMS, Notepad++, etc. are supported through the disk adapter only, with an explicit `target_file_path` (their titles expose only a filename, so ScreenBot refuses to guess a path). ScreenBot now inspects every visible editor window, but only VS Code and Antigravity are trusted to show a clean buffer; all other editors are treated as *unknown* and their changes are queued for review even when the file happens to be saved. This favors safety over automation: expect to accept changes manually in those editors. The tri-state behavior is verified against synthetic window lists, not against a real install of each IDE, so per-IDE title markers and multi-window behavior remain a manual check. A hidden or minimized-to-tray editor with no visible window can still hold unsaved text; if no editor window is found at all, ScreenBot allows the write. Save the file first, or use the VS Code-family bridge extension.
2. **No native plugins for non-VS Code IDEs yet.** They use the common bridge protocol, but only the VS Code-family extension currently supplies exact-buffer context, diagnostics, and the pending-review UI. Pending changes for other IDEs are stored under `session_data/` and are not forced into the file, but there is no in-IDE review command for them. Binding these IDEs requires a manually configured `target_file_path`.
3. **Diagnostics are asynchronous.** The VS Code extension waits ~900 ms after an apply before reading diagnostics, and Visual Studio's Error List can lag further. A slow language server may report a new error after the gate has already passed. Disk targets provide no diagnostics at all; the syntax gate is the only syntax protection there.
4. **Caret-mode undo is internal.** Without a bound direct-sync file, `Ctrl+Alt+Z` restores ScreenBot's master snapshot, not text already typed into an editor. Use the editor's own undo for pasted text.
5. **OCR remains lossy.** Stability, consensus, append-only merging, and syntax/diagnostic gates reduce corruption but cannot prove that a line was read correctly. Small fonts, motion blur, unusual ligatures, and non-Latin identifiers still need a live-session check.
6. **The VS Code-family extension is not exercised in a real editor by CI.** It has a Node test suite (`npm test`) using a mocked `vscode` module covering apply/undo/expiry behavior; installing it into VS Code, Antigravity, Cursor, or Windsurf and exercising workspace edits, save, and diagnostics is still manual.
7. **Visual Studio DTE is simulated in tests, never driven for real.** It exists only when `pywin32` is installed; otherwise `Ctrl+Shift+F` cannot resolve the active path, and Visual Studio requires `target_file_path` and uses the disk adapter, inheriting the unknown-saved-state hold above. The per-thread COM, retry, minimal edit, undo-context, and abort paths are unit-tested with a fake DTE, but a real Visual Studio session must still confirm that breakpoints, bookmarks, and a single undo step survive an apply.
8. **Formatter is opt-in but whole-file.** `format_on_apply` / `screenbot.formatOnApply` runs the editor's document formatter, which may move code the user did not touch. It is deliberately off by default.
9. **Bridge local security.** The HTTP bridge binds only to `127.0.0.1` and requires a random token in the `X-ScreenBot-Token` header (query-string tokens are rejected) stored in `%APPDATA%\ScreenBot\bridge.json`. Any process running as the same Windows user can read that file and speak the protocol. This protects against remote access, not a compromised local account.
10. **Windows only.** Focus guards, Win32 key events, GDI capture, and the DTE adapter are Windows-specific. The test suite runs offline with mocked capture/injection boundaries, so a real class session is still the final integration test.
